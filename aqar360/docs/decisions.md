# Architecture and scope decisions — 2026-10-29

| ID | Decision | Evidence / consequence |
|---|---|---|
| ADR-001 | The full build prompt plus the user's four-phase summary is the working specification. | The master strategy DOCX was requested twice but is absent. Its exact numbered requirements, Appendix B schema, Appendix E cost table, Appendix F events and all 14 Appendix G test definitions cannot be verified. They are not invented or marked complete. |
| ADR-002 | Phase 0 only; stop for review before MVP development. | Later phases are disabled in server validation. Phase 1 items in the data model are designs, not implemented functionality. |
| ADR-003 | Contact is the canonical natural-person record. | Existing Contact email/phone child tables and Dynamic Links connect Customer/Supplier; Customer.customer_primary_contact and CRM Deal.contact already exist. Add CRM Lead.custom_aqar_contact; preserve source snapshots and historic lead identities. Do not merge people automatically on a shared phone/email. |
| ADR-004 | Extend real_estate Property and Property Unit. Reuse ERPNext Project for project registry. | Installed schemas are recorded in evidence/installed_metadata.json. Property has owner Dynamic Link, units have a Property link. Project receives domain fields later; do not create another generic Project. |
| ADR-005 | MariaDB, geographic hierarchy and coordinates first. | Overrides the strategy's reported PostgreSQL/PostGIS assumption. No PostGIS service until a demonstrated geographic need. |
| ADR-006 | Namespaced roles; least privilege, no automatic native role grants. | Aqar Finance/HR are not silently given broad Accounts/HR roles. Aqar Customer/Supplier have no desk access. Operational permissions require Phase 1 record-level tests. |
| ADR-007 | Reuse Frappe TOTP, Version, Workflow, Assignment Rule, Notification and Error Log. | TOTP mandatory for Aqar Admin/Manager/Finance/HR and native privileged roles on staging. Version is mutable by privileged database administrators; it is not an append-only audit solution. |
| ADR-008 | Development mounts only aqar360 source on the installed image; no development image rebuild. | Practical Python-only Phase 0 dev container using frappe_docker services. Existing image is baseline, not a newly published staging artifact. Build-tool/Next.js dev container extension is pending Phase 1. |
| ADR-009 | Local staging is a separate site/database on shared MariaDB/Redis. | User has no staging host/domain yet. It is not a deployed Oman-approved external staging environment. No real personal data or production release. |
| ADR-010 | AI gateway is the sole future provider boundary. | Upstream real_estate/ai/claude_client.py calls Anthropic directly. Do not configure real_estate_claude_api_key. No AI integration enabled. |
| ADR-011 | Block legacy tenant-portal mutations and invoice PDF endpoints on Aqar sites. | submit_maintenance_request uses ignore_permissions without validating the tenant's unit. Custom whitelist override denies both legacy actions pending an isolated portal implementation. Upstream code remains untouched. |
| ADR-012 | Configure encryption locally; require restic outer encryption off-server. | Frappe GPG encrypts DB/files but leaves config JSON sensitive and may log encryption failure without failing. Verify decryption of every latest backup artifact and use restic for the full set; keep credentials/key escrow outside Git. Remote destination absent, so off-server transfer is not active. |
| ADR-013 | No legal/commercial defaults imply approval. | Fees, commissions, taxes, retention, content rights, jurisdiction, payment and WhatsApp route remain pending. Selected public campaign pages only is the safe initial publication policy. |
| ADR-014 | Keep production apps.json incomplete rather than invent a repository URL. | Custom app is in a monorepo subdirectory. It needs an approved subtree export repository (or supported build packaging) before bench can clone it via apps.json. apps.custom.example.json is an explicit nondeployable example. |


| ADR-015 | Use Frappe v16 IntegrationTestCase, locally aliased FrappeTestCase. | The installed v16 API exports IntegrationTestCase; seven real integration tests run with the native test runner. |
| ADR-016 | Repair two upstream Property metadata defects using Aqar fixtures. | owner_link referenced a missing owner_type; add custom_aqar_owner_type and redirect options. amenities was Table MultiSelect but Property Feature has only Data fields; convert metadata to Table, preserving child rows. No source edit or class override. |
| ADR-017 | Scope mandatory MFA to privileged roles after enabling it globally. | Frappe's System Settings automatically marks All for 2FA. Aqar clears that automatic blanket flag and preserves explicit privileged-role requirements; customer role remains unforced in the foundation test. |
| ADR-018 | Strategy V10 PDF supplied 2026-10-30; keep Frappe/MariaDB as the single source of truth instead of the strategy's PostgreSQL + n8n stack. | Appendix E's goals (no per-user licences, one database, no duplicate systems) are met by open-source Frappe, which already provides CRM/finance/HR/workflow/scheduler. Appendix F.5 allows backend scheduling without n8n; n8n remains optional for external integrations and never holds customer data. Requires a load test on the target VPS because the stack needs more RAM than Appendix E's smallest tier. See implementation_plan.md. |
| ADR-019 | Public submissions reuse an existing Contact only when every supplied identifier (email and phone) matches that same single Contact; any partial overlap creates a new Contact flagged as a duplicate candidate for human review. | Refines ADR-003 for public intake: identical email+phone is treated as the same person so repeat requests from different channels share one Customer 360 while keeping each request's source; shared single identifiers (family phone, shared email) never merge automatically. |
| ADR-020 | Domain audit for customer records logs decision fields only (status, budget, review outcome, source), never names, phones or emails. | The audit trail is append-only and cannot honour erasure requests; personal data stays in editable records governed by retention policy. |
| ADR-021 | Developer projects live in a dedicated Aqar Development Project registry, not ERPNext Project; supersedes the Project part of ADR-004. | ERPNext Project is internal job costing (tasks, timesheets, billing) and requires a Company, which staging does not have (setup wizard pending). Third-party developer projects are supply records with availability, verification, foreign-ownership and unit-type data. ERPNext Project remains for internal work (content orders, consulting jobs). Property.custom_aqar_project now links to the registry; no data existed to migrate. |
| ADR-022 | Match status is controller-managed (staff actions + engine), not a native Frappe Workflow. | Frappe workflow validation has no bypass, but the engine must withdraw matches when supply sells or a request closes and restore them when supply returns. Staff transitions go through aqar360.matching.actions.update_match with role and supply checks; any direct status edit is rejected. |
| ADR-023 | Matching runs as a background job after commit (deduplicated per record), synchronously only in tests. | Saving a property or request stays fast; the queue worker re-scores against all active requests or all supply. Volume is fine for a single-server Lean tier; revisit with indexing or batching if supply × active requests grows large. |
| ADR-024 | SLA timers are an Aqar record per (record, policy) driven by code bindings; targets live in editable Aqar SLA Policy records. Native CRM SLA stays for CRM Lead/Deal when CRM leads are used. | §8.3 needs one consistent pause/RAG/escalation model across requests, intakes, consultations and later content orders and campaigns. Business time uses Platform Settings (Sun–Thu 08:00–17:00 default) plus an optional Holiday List. |
| ADR-025 | Price-cut approval rules are seeded inactive. | Thresholds and approver roles are a business decision; an administrator enables them. Approvers editing within their own authority are allowed and audited; nobody can approve their own request. |
| ADR-026 | Customer-owned business data is built as editable placeholders and tracked in customer_inputs.md. Staging runs a placeholder company "Aqar 360 (Placeholder)" (OMR, Standard chart, FY 2026); production runs its own setup with the customer's real details. | The platform is delivered to a customer who supplies legal identity, VAT, prices, legal texts and provider accounts later. Seeding never overwrites a value the customer has edited. |
| ADR-027 | Aqar roles get narrow per-DocType grants for commerce (catalogue read, quotation drafting, Finance-only invoices/payments, "select"-only on Account for quoting staff) instead of broad ERPNext roles. | ERPNext checks the current user's Item read and Account select permissions while pricing; staff need exactly that, not access to the books (refines ADR-006). |
| ADR-028 | Customer accounts use Frappe website users with the Aqar Customer role; the website keeps the Frappe session id and CSRF token in httpOnly cookies and calls Frappe server-side. A customer sees records of Contacts carrying their own login email. | Email ownership is proven by Frappe's sign-up/reset email links; staff accounts are refused on the public site (they use the desk). Sign-up and reset answer identically whether or not the email exists (no enumeration). Logout ends the Frappe session server-side (POST with the session's CSRF token). |
| ADR-029 | Vault upload checks are layered and labelled honestly: allowlist + size + file signature + no macros always ("Basic Checks Passed"); ClamAV via clamd only when `aqar_clamav_host` is configured ("Clean (Antivirus)"). Files are read as raw bytes. | No antivirus engine runs on this PC; the label must not overstate protection. File.get_content() can return decoded text, which corrupted binary files in the first implementation (caught by tests). |
| ADR-030 | Every customer message goes through one Aqar Outbox record keyed by an idempotency key, rendered from an approved, versioned Aqar Message Template (approved versions are locked; approving a new version retires the old). Follow-up/marketing respect quiet hours, a weekly cap and the unsubscribed flag; transactional confirmations are never delayed. Lifecycle jobs run on the Frappe scheduler. | Appendix F.4/F.8: no double sends, consent per purpose and channel, sending failures never block the business action (3 attempts, then Failed + Error Log). Template wording is the customer's (customer_inputs.md) and changes without a deploy. "Delivered" mirrors the Email Queue "Sent" state, i.e. accepted by the mail server, not opened. WhatsApp uses the same outbox once the Phase 2 flag and a provider exist; until then it falls back to email. |
| ADR-031 | The public map uses MapLibre GL (open source) with a configurable vector style (default OpenFreeMap, no key); only records marked "Selected Public Page", Verified and Active/Limited appear; owner properties are placed in their area, never at exact coordinates, unless "Show Exact Location on Website" is ticked. Developer projects show exact pins. | No per-view map licence; the provider is swapped with one setting (customer_inputs.md). Exact owner addresses are personal data (§18) and are never sent to the browser, not just hidden. Locations stay in sync between the map pin, latitude/longitude and a pasted Google Maps link, so staff can use whichever is easiest. |
| ADR-032 | "Register interest" / "Ask" on the website stores the listing on the Search Request (Interested In = project or property, Interested Unit, Source Page), validated server-side against public listings; anything else is ignored, never an error. The matching engine flags the listing's matches with "The customer asked about this listing on the website" and, when the exact unit or unit-less property is outside the request's criteria but still available, creates a "Customer Interest" match (score 0) instead of dropping it. | Staff must see what the customer actually chose; the engine's criteria should not hide it. Keeping the rule inside evaluate() makes it stable under re-matching and supply updates (no side-created matches that the next run would withdraw). Website enquiries stay Search Requests (the CRM record since M2); the Frappe CRM Lead/Deal screens are not fed unless the team decides to work there. |
| ADR-033 | Replace Frappe/ERPNext with one Next.js app (public website + /admin) on Vercel, data in Neon Postgres (Drizzle ORM, `postgres` driver, pooled URL, prepare off). Staff login: bcrypt, database sessions (SHA-256 of the cookie token), httpOnly cookie on /admin, lockout after 5 failures in 15 minutes, first admin via a one-time /admin/setup with ADMIN_SETUP_TOKEN. Three roles: admin, manager, agent. | Free hosting with no card (the user pays hosting personally and the client will not), and a much simpler system for staff new to software. The Frappe app stays in the repo as the reference for rules and wording. Local development uses Neon too: Docker Desktop and PGlite were unreliable on the 8 GB PC (memory, disk, connection multiplexing). |
| ADR-034 | Operations stay "lite": quotes/invoices + payments + expenses give a cash view (income, client media money, expenses, receivable), not double-entry accounting; HR covers staff files, leave, payroll and renewals without statutory filings. | The client team is new to software and needs daily tools, not ERP books; the accountant can work from the CSV downloads. Client media money is tracked per invoice line so it never counts as revenue. |
| ADR-035 | Customers see a quote/invoice through a signed link (HMAC-SHA256 of the id with AUTH_SECRET) instead of an account or stored token. Rotating AUTH_SECRET invalidates all links. CVs and receipts use unguessable file names in Vercel Blob (public store). | No customer accounts in the simplified system; nothing extra to store or expire. Private Blob storage can replace public names later if the client requires it. |
| ADR-036 | Admin organised as two apps, CRM and ERP (Frappe-style switch + Apps page), without changing page addresses. | Staff asked for the Frappe layout; a short menu per app is easier for new users. Keeping URLs avoided rewriting links, actions and tests. |
| ADR-037 | Online payments through hosted checkouts only (Thawani checkout session, Paymob Intention + Unified Checkout); a payment is recorded only after server-side confirmation (Thawani session status, Paymob HMAC), for the exact balance, once (conditional status update), as method "online". Keys live only in environment variables. | No card data on our servers (PCI scope stays with the gateways). Return pages and webhooks can both arrive; idempotency keeps the books right. Paymob amount factor is configurable because its docs say "cents" and OMR has 3 decimals. |
| ADR-038 | Three apps (CRM, ERP, HR) chosen per person on the Staff page, on top of the role; a full-screen launcher after sign-in. | Mirrors Frappe's apps and keeps salaries and staff files out of sight for anyone without HR (strategy §26.7 least privilege). Admins always open everything. |
| ADR-039 | No group-level loading.tsx in the admin; instant feedback comes from a small client progress bar on clicks and saves. | In Next 15.5 a loading boundary above the pages stopped the page refreshing after server actions (found by the browser tests). |
| ADR-040 | Buttons never rely on their own name/value inside a server-action form; each decision button has its own action (formAction). | The clicked button's value was not included in the submitted data, so "Approve"/"Reject" did nothing (found by the browser tests). |
| ADR-041 | Refunds are negative payments created only after an admin, who is not the requester, approves; the customer receives a credit note. | Strategy §9.1 and §26.3 approval engine; keeps the finance summary and invoice status right without a separate ledger. |
| ADR-042 | WhatsApp through Meta's Cloud API directly (no BSP), templates mapped per message in the admin; automatic messages need WhatsApp consent even for service messages; staff free text only inside the 24-hour window. | Strategy §25.2 open decision "Meta direct vs BSP": direct has no middleman fees and is enough for one number; consent and window rules follow Meta policy and strategy F.4. |
| ADR-050 | Automated tests use a separate database (`aqar_test`) on the same Neon server and refuse to run against any other; live checks are read-only. Database backups are not stored in GitHub while the repository is public. | Tests insert and delete rows; on the live database one bug could remove customer data. A second database on the same server is free and needs no new account. Workflow artifacts of a public repository can be downloaded by any GitHub user, so even an encrypted dump does not belong there. |
| ADR-049 | Croquis coordinates are stored as written (UTM, with the datum) and converted to WGS 84 in our own code (no projection library), checked against PROJ fixtures; PSD93 uses EPSG:1439. Staff choose per plot whether it is public; a public plot reveals the exact location. Nearby places come from OpenStreetMap through public Overpass servers with a 30-day cache per grid cell. | Keeping the original numbers means a wrong datum can be fixed later without re-reading the croquis. A few hundred lines replace a large dependency and run in the browser for the live preview. The datum choice moves a plot ~380 m, so the preview shows both when the sheet does not say. OSM is free and covers Oman well; caching respects the free servers' usage policy. |
| ADR-048 | ID photos are read by the AI and never stored (staff upload to the document vault when a copy is needed). The listing card is drawn on a canvas in the staff member's browser, not on the server. Offline field actions are queued on the phone and applied once by id; only the Field screen is cached, and the cache is dropped when the session ends. | Least personal data (strategy §18). Server image libraries do not shape Arabic text; browsers do. A small, idempotent sync covers what staff do on site (arrival, outcome, notes) without making the whole admin offline-capable or keeping private pages on shared phones. |
| ADR-047 | The public chat assistant only reads public, verified data and creates leads through the same intake function as the website forms (its own per-visitor and daily limits replace the captcha); it is off by default. Agreements are fixed by a SHA-256 of title and text when sent and signed with typed name + drawn signature on a signed link; signing is refused if the stored text no longer matches. | One lead path keeps validation, consent and duplicate handling identical. A public AI must not see private data or run up costs unseen. The hash makes later edits detectable; typed name, drawing, time and device are the evidence an electronic signature usually needs (the customer's lawyer confirms the wording). |
| ADR-046 | Time-based jobs that need to run more often than the daily Vercel cron (request reassignment) run opportunistically after admin page renders (`after()`), claimed with one atomic "insert … on conflict … where older than 10 minutes" statement; the daily cron is the safety net. Owners see aggregates only; market medians need at least 3 comparable listings. | The free Vercel plan allows one cron run a day; staff use the admin all day, so checks run when they matter without a paid scheduler or a GitHub secret. The atomic claim keeps parallel servers from double-running. Privacy (strategy §18): owners learn about interest, never about the people. |
| ADR-045 | Customers book viewings themselves only for properties staff already sent them, from the signed portal link; free times come from opening hours in Settings minus the agent's and the property's other viewings, re-checked under a per-property advisory lock inside the booking transaction. Viewings stay timeline activities (source "online"), not a separate calendar table. | Keeps "staff approve before the customer hears of a property" (ADR on matching) and needs no customer accounts. Reusing activities means reminders, results, the field app and reports work unchanged. The lock runs on the transaction's own connection because production allows one database connection per function. |
| ADR-044 | Outside-service keys (Resend, Thawani, Paymob, WhatsApp, Anthropic) are entered by an admin in Admin → Integrations, like n8n credentials: stored in `settings` as `integration:<id>`, secret fields sealed with AES-256-GCM (key from AUTH_SECRET), never sent back to the browser (last 4 characters only), every save/test/removal audited without values. Each service has an on/off switch and a "Save and test" check that calls the provider (test email to the admin, Thawani session list, unpaid 1 OMR Paymob intention, WhatsApp number lookup, Anthropic model lookup). Environment variables remain a fallback; a saved service ignores them. Reads are cached 15 s per server instance. Supersedes the "keys only in environment variables" part of ADR-037. | The client's admin must be able to connect their own accounts without a developer, Vercel access or a redeploy. Encryption keeps a database leak from exposing working keys; rotating AUTH_SECRET means re-entering them (the page says so). The test call turns "it should work" into a visible green or red status. |
| ADR-043 | AI features use Claude through the official Anthropic SDK with read-only tools scoped to the asking user's apps and role; drafts are never saved without a person. | Strategy §26.8 and Appendix G: "AI finds, humans verify"; prompt injection handled by treating tool data as data and giving the model no write tools. |
